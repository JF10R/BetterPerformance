# Review: 0.4.7 to 0.4.10, 2026-09-16 to 2026-09-18

Scope: commits `6dcbe9b` (0.4.7), `5679132` (0.4.8), `b9126e7` (0.4.9) and the 0.4.10 tree,
plus the two game updates (1.0.14 on 09-17, 1.0.15 on 09-18) that landed in the middle.
Each finding is one line with a location; the fix column says what 0.4.10 did about it.

## Verdict

The work holds. Every native contract passes on both installations, three isolated runs and a
pre/post-update status comparison show no regression, and the two real defects found in that
period were ours, found by our own review, and fixed before either fired. The process defects
were worse than the code defects: twice in two days the previous game build was destroyed
before it could be diffed, and the contract harness had been hiding failures for an unknown
number of runs.

## Good

- The 1.0.14 pre/post status comparison (`.qa/runs/20260917T014402Z-3cc8a5` against the same-day post-update runs) answered "is the mod compatible" with evidence rather than with a green build; it also proved two suspicious statuses pre-existing.
- Every agent claim that mattered was re-derived before acting: the private `CreateNewZDO(ZDOID, Vector3, int)` overload and its two callers, the ownership audit's "unknown" server keys (both already on), the terrain "unexposed" misreading, the join agent's un-measured minimap fix (measured: `minimap_cache_status=installed`).
- The 1.0.15 terrain supersession was caught by the module's own `Verify` before any test ran: it declined to install on the new build, so vanilla behaviour was already in force. The self-refusing-contract pattern paid for itself.
- Two-sided contracts: the biome check fails if the cache branch ever returns; the terrain check fails if the per-texel save ever returns. Superseded behaviour cannot silently come back.

## Improvements made in 0.4.10

- `IlFingerprint` replaces the raw-IL pins (above). Audit of the other IL-dependent checks: the minimap cache hashes closure IL into its *key*, which is version-keyed anyway so token churn only costs one regeneration per game build; the terrain and smelter validators read IL structurally and are token-free. No other raw pin exists.
- The harness prints the installed game version per installation; `check-game-update.ps1` surfaces it.
- The game-update guide archives the old build before decompiling and reads the harness's whole failure list, not its first entry. The 1.0.14 server build is archived; every non-framework assembly (game, Unity modules, BepInEx, the installed plugins) is now decompiled locally.
- `TerrainSaveCoalescing` is removed (superseded by 1.0.15; this installation always runs the latest build). The terrain attribution telemetry stays.
- Loot visibility now covers trees, logs, plain rocks and destructibles with a drop table (owner `ZNetScene.Destroy` on an owned ZDO, remote `OnZDODestroyed`), counts t0 events per source, counts `TreeLog` as loot, and exports the live `item_drop_instances` population.
- `host_net_*`: the game's own ping, byte rates and link quality per interval, so the network legs above have a known floor.
- `AGENTS.md` carries the nine lessons from these three days so the next agent does not relearn them.

## 0.4.8 (delegated review, verified before acting)

| Severity | Finding | Fix |
| --- | --- | --- |
| BUG | `SmelterCatchupBudget.cs`: `BeforeUpdate`/`AfterUpdate`, the only resets of `gateCalls`, live in the best-effort telemetry set. If that install failed on a future build (`Smelter.Spawn`/`RemoveOneOre` renamed), the transpiler still installed and `Threshold()` returned `+Inf` for every smelter forever after eight loop tests. Latent: telemetry is `enabled` on 1.0.15. | Budget refuses to install unless telemetry is enabled (`Status = unavailable_telemetry`). |
| BUG | `DungeonSpawnSlicing.cs` `PlayerInsideBounds`: rebuilt `Generate`'s y-centre from `m_originalPosition`, which `ZoneSystem.SpawnLocation` assigns only in Full/Ghost mode (`ZoneSystem.cs:2438-2478`) and which is not in the ZDO — a client reads zero. A player inside a custom-interior dungeon could be judged outside, slicing would engage, and rooms would be placed under them across frames. `SliceRoomSpawnEnabled` is on for this client. | Centre y on the generator, double the vertical extent, add a distance gate; each error widens "inside", whose only consequence is the native spawn. Doc corrected. |
| BUG | `Finish` drops the entry before the native release (it must: the release prefix refuses while the entry is pending), so a throw from `SnappAll`/`ReleaseHeldReferences` made the catch abandon `Queue[0]` — by then the *next* dungeon, released early with rooms unplaced. | The slice in hand is held outside the loop and abandoned instead. |
| RISK | `Drop` skipped `Pending.Remove` for a destroyed generator (Unity `!= null` is false for a dead object that is still the dictionary key), pinning it and its room array. | Reference-equality check. |
| RISK | `MapPrecompression.cs`: the policy's `inFlight`/`resultPending` are plain bools written by the worker under `Gate` and read/advanced by the main thread outside it. A stale read could make `Dispatch` throw and the pump's catch `Release("failed")` the module for the session. | `Evaluate`, `Dispatch` and `Adopted` now run under `Gate`; `failures`/`published` are atomic on both threads. |
| NIT | `sliceMsMax`/`spanFramesMax` are plain read-modify-write maxima drained with `Interlocked.Exchange`. Both sides are the main thread, so nothing is lost today. | Not changed. |
| NIT | `DefaultIterations = 8` records no tradeoff. | Not changed. |

Kept as the pattern: the smelter `Validate` proves the whole loop shape, not just the constant,
and `Single()` makes an ambiguous match a hard failure; the pre-compression snapshot copies the
bit arrays and flattens pins on the main thread so the worker touches only an instance-local
`ZPackage`; correctness rests on the cache's full-input byte comparison, never on the change
signal; `Finish` reproduces the native tail in native order.
